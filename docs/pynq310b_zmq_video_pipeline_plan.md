# PYNQ-Z2 -> 310B 视频链路方案草案

## 1. 目标

在 PYNQ-Z2 侧完成 USB 摄像头采集、按比例可配置 ROI、轻量 ISP 处理，并将处理后的 8bit 量化数据通过 ZeroMQ 发送到接收端。当前阶段先在笔记本端完成接收、解析和可视化验证，后续再切到 310B。

约束条件如下：

- 输入：USB 摄像头，640x480，30fps，RGB
- ROI：按比例配置，运行时可更新，关键帧生效
- ISP：必须包含白平衡、色彩转换、降噪、gamma
- 输出：ISP 后的 8bit 量化数据
- 通信：先用 ZeroMQ 快速落地
- 实时性：端到端延迟目标小于 50ms，允许少量丢帧，上限 2%
- 调试方式：PYNQ 实机采集发送，WSL/笔记本接收和可视化

## 2. 推荐数据路径

### 2.1 采集与处理

1. USB 摄像头采集 RGB 640x480@30。
2. 在 PYNQ 侧执行 ROI 裁剪，ROI 使用归一化比例坐标表示：`x`, `y`, `w`, `h` 均在 `[0, 1]`。
3. ROI 内执行轻量 ISP：
   - 白平衡
   - RGB -> YUV420 或 YUV420 内部中间格式
   - 降噪
   - gamma
4. 输出按 8bit 量化，作为发送负载。
5. 通过 ZeroMQ 发送给接收端。

### 2.2 为什么推荐 YUV420

当前阶段建议把 wire format 定为 YUV420 8bit planar。

优点：

- 带宽更低，符合 50ms 目标。
- 更接近摄像头和视频链路的常见中间格式。
- 便于后续在接收端做显示、存盘或再转换。

缺点：

- 不能直接作为大多数推理网络的输入张量。
- 色度分辨率低于 RGB，调试时需要还原显示。

结论：

- 传输格式优先选 YUV420 8bit planar。
- 笔记本端接收后再还原成 BGR 用于可视化。
- 310B 端后续再按模型需要做进一步转换。

### 2.3 张量布局建议

如果后续必须给模型输入，常见布局是：

- HWC：适合可视化和 OpenCV 操作
- CHW：适合推理框架输入

但在当前“快速工程落地”阶段，建议不要把网络传输格式设计成 CHW。原因是：

- CHW 需要额外 transpose
- 传输和调试都更复杂
- 对当前阶段的延迟收益不明显

所以建议：

- 传输层：YUV420 planar
- 接收显示层：转 BGR
- 模型输入层：由 310B 侧按需转换成 CHW 或其他模型格式

## 3. 运行时参数

建议支持以下运行时参数：

- `roi_x`, `roi_y`, `roi_w`, `roi_h`
- `wb_r`, `wb_g`, `wb_b` 或自动白平衡开关
- `denoise_mode`
- `gamma`
- `frame_id`
- `timestamp_ns`

其中 ROI 修改采用“下一关键帧生效”的策略，避免半帧切换造成图像撕裂或状态不一致。

## 4. ZeroMQ 通信设计

### 4.1 推荐模式

- 视频流：PUB / SUB
- 控制通道：REQ / REP

说明：

- PUB / SUB 用于持续推流，满足视频数据单向传输。
- REQ / REP 用于修改 ROI、gamma、白平衡参数等控制命令。

### 4.2 帧头建议

每帧建议带一个固定长度帧头，字段如下：

- `magic`：用于快速校验协议
- `version`：协议版本
- `frame_id`：帧序号
- `timestamp_ns`：采集时间戳
- `width` / `height`
- `pixel_format`：例如 `YUV420P8`
- `roi_x`, `roi_y`, `roi_w`, `roi_h`：归一化 ROI
- `payload_len`
- `white_balance_mode`
- `gamma`
- `checksum` 或 `crc32`

建议将帧头和负载分开传输，或者同一消息中采用多帧 part。

### 4.3 传输粒度

由于当前目标是调试和快速落地，建议先按“整帧消息”发送，不做分片。理由：

- 640x480 + ROI 后数据量在可接受范围内
- ZeroMQ 在局域网内跑整帧更简单
- 先验证稳定性，再考虑分片和零拷贝优化

如果后续发现单帧过大或抖动明显，再升级为：

- 帧内分片
- 发送端 HWM 控制
- 接收端丢旧帧保新帧

## 5. 延迟预算建议

按 640x480@30 的目标，建议做如下预算：

- 采集：10~15ms
- ROI + 轻量 ISP：10~15ms
- ZeroMQ 打包与发送：2~5ms
- 局域网传输：1~5ms
- 接收端解析与显示：5~10ms

总预算目标：< 50ms

允许的丢帧率上限 2% 时，建议接收端采取“保最新帧”策略，不阻塞显示线程。

## 6. 阶段计划

### 阶段 A：架构与协议冻结

目标：

- 冻结输入、输出、帧头、控制通道、ROI 更新规则
- 明确 PYNQ 侧和接收端的数据边界

交付物：

- 本文档
- 协议字段定义
- 参数说明

### 阶段 B：最小可运行工程骨架

目标：

- PYNQ 侧能采集一帧或连续帧
- 完成 ROI 裁剪和基础 ISP 流水线
- 用 ZeroMQ 发到笔记本
- 接收端可视化显示

交付物：

- 发送端程序
- 接收端程序
- 可运行的命令行参数

### 阶段 C：稳定性和时延优化

目标：

- 连续稳定运行 30 分钟
- 统计端到端延迟和丢帧率
- 优化拷贝次数、缓存策略和线程模型

交付物：

- 延迟统计报告
- 丢帧统计报告
- 参数调优建议

## 7. 当前仓库现状判断

现有 `code/communication/zmq_pub.c` 和 `zmq_sub.c` 只是 64B 负载的延迟测试骨架，不适合作为视频流最终实现。下一步建议在 `code/communication/` 下新增视频流版本，而不是直接在当前测试程序上堆功能。

## 8. 下一步建议

如果你同意这个方向，下一步最适合做两件事：

1. 先写一版 `video_pub` / `video_sub` 的最小工程骨架，先跑通协议和显示。
2. 再把采集、ROI 和轻量 ISP 填进去。
